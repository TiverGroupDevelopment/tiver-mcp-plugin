# Правила моделирования семейств

Здесь лежат профили правил: общие правила, пакеты и профили проектов. Профиль — папка:

```
rules/
├── README.md              этот файл
├── _шаблон/               заготовка профиля для нового проекта
├── global/                общие правила (kind: global) — для любого семейства
├── adsk/                  пакет (kind: pack) — параметры ADSK
└── <Проект>/              профиль проекта (kind: project)
    ├── profile.json       машинная часть: наследование, ФОП, проверки и пороги
    ├── ПРАВИЛА.md         текст правил одним файлом…
    ├── правила/<раздел>.md   …или по разделам
    └── ФОП….txt           файл общих параметров проекта
```

Сейчас есть: `global`, `adsk`, [Альтерпласт](Альтерпласт/ПРАВИЛА.md) (`alterplast`) и [Альтерпласт: коллекторы](Альтерпласт_коллекторы/ПРАВИЛА.md) (`alterplast-multiport`).

## Слои: общее → пакеты → проект

Профиль наследует другие через `extends`. Слои складываются от общего к частному:

```
global → adsk → alterplast → alterplast-multiport
```

В профиле записано только то, что он добавляет или меняет. Правка порога в `alterplast` сама доходит до `alterplast-multiport`.

| Что | Как складывается |
|---|---|
| `checks` | по ключу проверки; поля дополняются и заменяются по одному. `"ключ": null` отключает унаследованную проверку, `"поле": null` убирает поле |
| `conventions` | по ключу, значение заменяется целиком; `null` убирает ключ |
| `manualRules` | по номеру правила; `{ "rule": "X", "remove": true }` убирает унаследованное |
| `sharedParameterFile`, `revitVersion` | свои или ближайшего родителя |
| тексты правил | всех слоёв, от общего к частному |
| `id`, `name`, `version`, `scope`, `activation`, `examples` | только свои |

Пример: профиль коллекторов заменяет порог и номер правила, не повторяя список запрещённой геометрии, и отключает проверку, которая к нему не подходит:

```json
"extends": "alterplast",
"checks": {
  "singleGeometry": { "rule": "MP-04", "maxForms": 10 },
  "connectorsLinked": null
}
```

## Какой профиль применяется

`get_family_rules` и `check_family_rules` принимают `profile`, но он не обязателен:

1. `profile` указан — этот профиль со всеми слоями. Агент указывает профиль проекта, когда проект назван в задаче.
2. `profile` не указан — только общие правила `global`.

Команды моделирования (`new_family`, `create_family_*`, …) правил не знают и работают одинаково для любого проекта. Правила применяются, только когда агент вызывает эти два инструмента.

### Эталонные семейства и корень данных

Исходные данные, эталоны и результаты лежат вне git, у каждого на своём диске. Поэтому в профиле путь к эталону (`examples`) пишется относительно корня данных:

```json
"examples": { "good": "Альтерпласт/rvt/rfa/Кран_шаровой_полный_проход_TEBO_ВН_ВН_бабочка.rfa" }
```

Корень задаёт переменная `REVIT_MCP_DATA_DIR` (например, `D:\Семейства`). `get_family_rules` отдаёт полные пути и отмечает, найден ли файл. Без переменной путь остаётся относительным, а в ответе есть подсказка. Абсолютный путь в `examples` сверка (`check-integrity.mjs`) считает ошибкой.

## Как агент работает с профилем

| Шаг | Инструмент | Что даёт |
|---|---|---|
| Какие профили есть | `list_family_rule_profiles` | профили, их вид, наследование, разделы |
| Перед моделированием | `get_family_rules` | тексты правил всех слоёв, соглашения, путь к ФОП, обязательные параметры с GUID |
| Только один раздел | `get_family_rules section: "geometry"` | проверки и тексты этого раздела |
| Во время работы | обычные команды семейств | параметры берутся из ответа `get_family_rules` |
| После моделирования | `check_family_rules` | `pass` / `warn` / `fail` по каждому автоматическому правилу и список правил для ручной проверки |
| Часть проверок | `check_family_rules only: ["mep"]` | ключи проверок, номера правил или разделы |

`check_family_rules` проверяет текущее семейство (сессию, активный документ, `familyName` из проекта) или файл по `path`. Только читает.

## Разделы

Разделы одни и те же для наборов команд и для правил (список — в [sections.json](../sections.json)):

| Ключ | Раздел |
|---|---|
| `session` | Сессия и файлы |
| `parameters` | Параметры и свойства |
| `geometry` | Геометрия |
| `nested` | Вложенные семейства |
| `graphics` | Графика и материалы |
| `mep` | Коннекторы (MEP) |
| `checks` | Проверки и отчёты |
| `service` | Служебные |
| `project` | Модель проекта |

Раздел автоматической проверки задан самой проверкой (см. таблицу ниже). Текст правил делится на разделы через `rulesFiles`:

```json
"rulesFiles": { "parameters": "правила/параметры.md", "geometry": "правила/геометрия.md" }
```

Профиль с одним файлом (`rulesFile`) тоже работает: при запросе раздела его текст отдаётся целиком. Так устроены `alterplast` и `alterplast-multiport`.

## profile.json

```jsonc
{
  "id": "alterplast",                 // короткий ключ
  "name": "Альтерпласт",
  "kind": "project",                  // global | pack | project
  "status": "validated",              // draft — ждёт проверки человеком; validated — проверен
  "version": "1.1",
  "extends": ["global", "adsk"],      // родители, от общего к частному
  "scope": "…",                       // к каким семействам относится
  "activation": "…",                  // когда применять
  "revitVersion": "2019",
  "sharedParameterFile": "ФОП2019.txt", // путь относительно папки профиля
  "rulesFile": "ПРАВИЛА.md",          // или rulesFiles по разделам
  "manualRules": [{ "rule": "ALT-08", "title": "…", "section": "geometry" }],
  "conventions": { … },               // соглашения для агента
  "checks": { … }                     // автоматические проверки
}
```

### Проверки (`checks`)

Каждая проверка — универсальная функция команды `check_family_rules`. Профиль включает её ключом и задаёт пороги, а `rule` связывает с номером правила в тексте. GUID обязательных параметров сервер берёт из ФОП профиля сам.

| Ключ | Раздел | Что проверяет | Настройки |
|---|---|---|---|
| `category` | parameters | категория семейства | `allowed`: список `OST_…` |
| `partType` | parameters | тип детали | `allowed` |
| `requiredParameters` | parameters | общие параметры есть, GUID совпадает с ФОП, тип/экземпляр | `parameters`: `[{name, instance?}]` |
| `parameterGroups` | parameters | параметры в своих группах | `parameters`: `{имя: группа}` |
| `extraParameters` | parameters | лишние параметры | `forbid`, `allowText` |
| `lookupTable` | parameters | есть таблица выбора и формулы `size_lookup`, мало типов | `maxTypes` |
| `lookupDefaults` | parameters | значение по умолчанию `size_lookup` у текстов | `parameters`, `text` |
| `lookupDecimals` | parameters | знаков после запятой в таблице выбора | `maxDecimals` |
| `materialParameter` | graphics | материал всех твёрдых форм и вложенных связан с параметром | `name` |
| `nesting` | nested | глубина вложенности и число вложенных экземпляров | `maxDepth`, `maxCount` |
| `nestedShared` | nested | у вложенных снята галочка «Общий» | — |
| `connectorSystem` | mep | классификация системы трубных коннекторов | `pipe` |
| `connectorsLinked` | mep | коннекторы связаны попарно | — |
| `connectorOrientation` | mep | ось Y коннекторов направлена вверх | `up` |
| `connectorOrientationByDirection` | mep | ось Y по направлению коннектора | `up`, `verticalY` |
| `connectorDepth` | mep | коннектор в глубине детали | `requireInside` |
| `mainRun` | mep | магистраль: 2 коннектора на оси, связаны | `axis`, `toleranceMm` |
| `singleGeometry` | geometry | число форм и запрещённая геометрия | `maxForms`, `forbid` |
| `labelsOnPlanes` | geometry | параметры размеров на опорных плоскостях | `allowGeometryLabels` |
| `origin` | geometry | центр габаритов в начале координат | `toleranceMm`, `axes` |
| `referencePlanes` | geometry | опорные плоскости не длиннее геометрии | `maxLengthFactor`, `ignoreTemplatePlanes`, `severity` |

Новая проверка добавляется в `FamilyRuleChecker.cs` (`commandset/Family/Utils/FamilyEditor/`) под новым ключом, её раздел — в `CHECK_SECTIONS` (`server/src/utils/familyRules.ts`).

## Новый проект

Одной командой (создаёт профиль правил и остальные заготовки проекта):

```
.\scripts\new-project.ps1 -Id proplan -Name "ПроПлан"
```

Вручную:

1. Скопировать `_шаблон` в `rules/<Проект>/`, положить ФОП проекта.
2. Заполнить `profile.json`: id, область, условие применения, `extends` (обычно `["global"]` или `["global", "adsk"]`).
3. Добавить только свои проверки и те, что меняются относительно родителей.
4. Описать правила по разделам в `правила/<раздел>.md`: номер, суть, как делать, как проверять, исключения.
5. Проверить: `node scripts/check-integrity.mjs` и `check_family_rules profile: "<id>" path: "<эталон.rfa>"` — эталон должен проходить.

## Перенос правила в общие

Правило проекта становится общим после проверки человеком. Критерии и порядок — в [PROMOTION.md](../PROMOTION.md).

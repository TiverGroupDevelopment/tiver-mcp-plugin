# Глобальное и проектное: команды, правила, перенос

Команды и правила делятся на общие (глобальные) и проектные. Общие используются в любом проекте моделирования семейств. Проектные рождаются под конкретный проект и переходят в общие после проверки человеком.

## Где что лежит

| Что | Общее | Проектное |
|---|---|---|
| Правила | `rules/global/`, пакеты (`rules/adsk/`) | `rules/<Проект>/` с `"extends"` |
| Наборы команд | набор **Global** | набор проекта, например **Alterplast** |
| Код команд | все в одном месте: модель проекта — `commandset/Commands/`, `Services/`; семейства — `commandset/Family/Commands/FamilyEditor/`, `Family/Services/FamilyEditor/` | там же |
| Инструмент сервера | `server/src/tools/` | там же |
| Принадлежность к набору | `"sets": ["Global"]` в `command.json` | `"sets": ["Global", "Alterplast"]` или `"sets": ["Alterplast"]` |
| Скрипт без сборки | — | `projects/<id>/scripts/<имя>.cs` |
| Исходные данные (ИД), результаты | — | вне git: локальный диск, Google Drive |

### Как устроены наборы

Код всех команд лежит в одном месте и собирается в одну сборку `RevitMCPCommandSet.dll`. Набор — это не папка и не DLL, а список: какие команды к нему относятся, говорит поле `sets` у каждой команды в `command.json` (корень репозитория).

```json
{
  "commandSets": [
    { "name": "Global", "description": "Общие команды" },
    { "name": "Alterplast", "project": "alterplast", "description": "Все команды проекта Альтерпласт" }
  ],
  "commands": [
    { "commandName": "create_wall",                   "sets": ["Global"] },
    { "commandName": "new_family",                    "sets": ["Global", "Alterplast"] },
    { "commandName": "create_family_inspection_copy", "sets": ["Alterplast"] }
  ]
}
```

- Команда входит в столько наборов, сколько перечислено в `sets`. Код у неё один: исправление сразу доходит до всех наборов.
- `commandSets` описывает наборы. `project` связывает набор проекта с его профилем правил (`rules/<проект>`).
- Инструменты, реализованные в самом сервере, записаны в `server/command.json` с тем же полем `sets`.

| Набор | Команд | Что входит |
|---|---|---|
| Global | 84 C# + 12 серверных | всё, что пригодится в любом проекте: модель проекта, топография, выполнение кода, редактор семейств, запуск Revit, правила |
| Alterplast | 56 | все команды прежнего набора семейств: 55 общих (входят и в Global) и 1 только для проекта — `create_family_inspection_copy` |

В окне настроек плагина в Revit команды сгруппированы по наборам. Команда из двух наборов видна в обоих, галочка у неё одна. В реестр плагина она попадает один раз. Агенту доступны все команды в любой сессии.

Пространства имён кода семейств — `RevitMCPFamilyCommandSet.*` (исторические). На работу это не влияет.

## Три ступени команды

| Ступень | Что это | Когда переходить дальше |
|---|---|---|
| 1. Скрипт | C#-код для `send_code_to_revit`, сохранённый в `projects/<id>/scripts/`. Сборка и перезапуск Revit не нужны. Запуск — `run_project_script` | скрипт понадобился второй раз или стал длиннее экрана |
| 2. Команда проекта | C#-команда и инструмент сервера в общем коде, `"sets": ["<Набор проекта>"]`, `"status": "experimental"` | команда пригодится при моделировании вообще, а не в одном процессе проекта |
| 3. Общая команда | в `sets` добавлен `"Global"`; после проверки — `"status": "validated"` | — |

Перенос со ступени 2 на 3 — одна правка: в `sets` команды добавляется `"Global"`. Код и имя команды не меняются, проект пользуется ею как прежде.

Новый проект заводит свой набор в `commandSets` и добавляет его имя в `sets` тех команд, которыми пользуется.

## Критерии общей команды

Команда общая, если выполняется всё:

1. **Пригодится при моделировании вообще.** Её можно использовать в другом проекте и дорабатывать дальше; это не узкий процесс одного проекта (например, копия для инспектора по регламенту Альтерпласта).
2. **Нет привязки к проекту в коде.** Нет имён параметров (`ADSK_…`, `DN1`), категорий, путей, порогов. Всё проектное приходит аргументами или из профиля правил.
3. **Описание понятно без проекта.** В описании инструмента нет отсылок к проекту и его правилам.
4. **Проверена.** Есть запись в отчёте тестирования: штатный случай, отказ с понятным сообщением, поведение при ошибке Revit. Проверено на версиях Revit, с которыми работают проекты.
5. **Сверка проходит.** `node scripts/check-integrity.mjs` без ошибок.

## Критерии общего правила

Правило общее, если его готовы применять, когда проект не назван:

1. **Не зависит от заказчика и стандарта.** Требование стандарта (ADSK и т. п.) — это пакет, а не общее правило.
2. **Действует в двух проектах** или очевидно следует из устройства Revit.
3. **Порог не спорный.** Спорный порог общий слой не задаёт: его задаёт проект.
4. **Есть номер по разделу** (`GEO-01`, `PAR-01`), а не по проекту. В проекте старый номер остаётся через `"rule"`: `"singleGeometry": { "rule": "ALT-10" }`.
5. **Профили проектов после переноса дают тот же результат** на эталонных семействах (`check_family_rules`).

Пакет (`kind: pack`) — промежуточный слой: правила стандарта или типа изделий, общие для нескольких проектов, но не для всех.

## Порядок переноса

1. Автор открывает запрос на слияние (PR) с меткой «в общие» и заполняет чек-лист ниже.
2. Проверяющий — человек, не автор. ИИ может подготовить разбор, решение принимает человек.
3. После слияния: у команды `"status": "validated"`, у профиля правил `"status": "validated"`.

### Чек-лист для команды

- [ ] Где ещё, кроме своего проекта, пригодится команда
- [ ] В коде нет имён параметров, категорий, путей и порогов проекта
- [ ] Описание инструмента без отсылок к проекту
- [ ] Запись в отчёте тестирования, версии Revit
- [ ] В `sets` команды добавлен `"Global"`
- [ ] `node scripts/check-integrity.mjs` — без ошибок

### Чек-лист для правила

- [ ] В каких двух проектах правило действует
- [ ] Правило не требование стандарта или заказчика (иначе — пакет)
- [ ] Новый номер по разделу, в проектах старый номер сохранён через `"rule"`
- [ ] Текст правила перенесён в `rules/global/правила/<раздел>.md`, в проекте остались только отличия
- [ ] `check_family_rules` на эталонных семействах проектов — тот же результат
- [ ] `node scripts/check-integrity.mjs` — без ошибок

## Ветки

- `main` — общее и все проекты. Проект — это папки и профиль, а не ветка.
- Работа идёт в коротких ветках под задачу; проектные папки изолированы, поэтому слияния не конфликтуют.
- Выпуск проекта фиксируется тегом (`alterplast-1.1`): он показывает, на каких версиях общих команд и правил проект проверен.

- **Наборы.** Набор Alterplast — все 56 команд прежнего набора семейств `RevitMCPFamilyCommandSet`. 55 из них входят и в Global: в их коде нет привязки к проекту (имена параметров, оси, пороги приходят аргументами или из профиля правил), и они нужны при моделировании любых семейств. Только в Alterplast — `create_family_inspection_copy`: копия семейства для инспектора по процессу Альтерпласта (правило ALT-12 сейчас этот процесс приостанавливает). 29 команд модели проекта (стены, топография, выполнение кода) и 12 инструментов сервера — только в Global.
- **Статусы.** `"status": "experimental"` у 13 команд семейств, которых нет в отчёте тестирования от 11.11.2026: `set_family_parameter_values`, `lock_family_sketch`, `export_family_lookup_tables`, `list_project_families`, `place_family_in_project`, `open_family_in_editor`, `create_family_model_text`, `get_family_mass`, `diagnose_revit`, `dismiss_revit_dialog`, `check_family_rules`, `create_family_inspection_copy`, `setup_family_connectors`. Остальные — `validated`. Экспериментальные команды в Global — общие по назначению, но ещё не проверены.
- **Правила.** `global` (GEO-01…GEO-03) и `adsk` (ADSK-01, ADSK-02) — `"status": "draft"`: состав взят из профиля `alterplast` 1.1.
- **Кандидаты в общие правила** из проекта Альтерпласт: ALT-04 (вложенные не «Общие»), ALT-14 (центр в начале координат), ALT-21 (округление). Кандидаты в пакет «фитинги MEP»: ALT-05…ALT-07, ALT-19, MP-01, MP-02, MP-06.
